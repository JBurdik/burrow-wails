# Burrow MCP Server — Implementation Spec

**Status:** proposal / for review. No production code yet.
**Goal:** give Burrow-launched agents a real MCP server for sub-agent orchestration, replacing the file-request-dir `burrow spawn` transport, modeled on the **jean** reference implementation. Keep the existing file-based CLI working through the transition.

Reference impl cloned at `…/scratchpad/jean/src-tauri/src/` — files `jean_mcp_core.rs`, `jean_mcp_stdio.rs`, `jean_mcp_socket.rs`, `jean_mcp_config.rs`, `chat/jean_mcp.rs`.

---

## 0. Why change

Today an agent delegates by shelling out to the `burrow` script, which drops a request dir the frontend polls (`take_spawn_requests`, `Terminal.vue` 1 s poll). It works, but:

- Agents discover the CLI via a global skill doc — no typed tool schemas, no argument validation, no structured results.
- Result collection is a manual `burrow wait <token>` / `burrow collect` polling loop the agent has to remember to run.
- No principled recursion cap — a spawned agent can spawn agents can spawn agents. Only a soft, unenforced `max_agents` file (`bin/burrow:72-79`).

MCP gives the agent first-class tools (`spawn`, `create_worktree`, `collect_results`, …) with schemas, plus jean's clean depth-cap for runaway prevention. Crucially it reuses **the entire existing backend** — the MCP layer is a thin front door onto `take_spawn_requests` and the same Rust handlers.

---

## 1. How jean's MCP server works (the model we copy)

Three layers, two processes, **no HTTP port** — a local Unix socket instead.

### 1a. In-process socket server (Tauri side)

`jean_mcp_socket.rs` binds a Unix domain socket (`<app_data>/jean-mcp.sock`, chmod `0o600`) or a Windows named pipe.

```rust
// jean_mcp_socket.rs:74 (unix) / :157 (windows)
pub fn start_socket_server(app: AppHandle, path: PathBuf, token: String)
    -> Result<JeanMcpSocketHandle, String>
// jean_mcp_socket.rs:248
fn handle_socket_request(app: &AppHandle, expected_token: &str, line: &str) -> Value
```

Owns the live `AppHandle`, so tool logic runs **in-process** with full app state. Per connection it reads one newline-delimited JSON request, validates the bearer token (`crate::http_server::auth::validate_token`), then calls into the shared core `call_tool(app, name, args, source, depth)`. 30 s read timeout per connection.

### 1b. Stdio proxy (the thing the CLI actually launches)

`jean_mcp_stdio.rs` is launched by the third-party CLI as `<jean-binary> --jean-mcp-stdio`.

```rust
// jean_mcp_stdio.rs:19
pub fn run_stdio_server() -> Result<(), String>          // stdin/stdout JSON-RPC loop
// jean_mcp_stdio.rs:42
fn handle_message(...) -> ...                            // -> handle_protocol_message
// jean_mcp_stdio.rs:51
fn proxy_tool_call(req: ToolCallRequest) -> Result<Value, String>  // opens socket, forwards
```

It implements **no tool logic**. `initialize` / `tools/list` / `ping` answer locally from the static registry; `tools/call` is forwarded over the Unix socket to the in-process server (1a). Read 120 s / write 30 s client timeouts. The stdio process is a thin, disposable proxy; the socket server is the brain. This is what lets the tools run with real app state without exposing a network port.

### 1c. Shared core

`jean_mcp_core.rs` — transport-agnostic JSON-RPC router + static tool registry + dispatch.

```rust
// jean_mcp_core.rs:100
pub fn handle_protocol_message(body: Value,
    call_tool: impl FnMut(ToolCallRequest) -> Result<Value, String>) -> Option<Value>
// jean_mcp_core.rs:130   static registry
pub fn tool_registry() -> Value
// jean_mcp_core.rs:155 / :196   dispatch
pub fn call_tool(app, name, arguments, source, depth) -> ...
fn run_tool(...) -> ...   // -> crate::http_server::dispatch::dispatch_command(app, cmd, json)
```

Every tool is a thin wrapper over an existing backend command (`dispatch_command`). `MCP_PROTOCOL_VERSION = "2024-11-05"`, `serverInfo.name = "jean"`.

### 1d. Socket wire protocol

Newline-delimited JSON, one request / one response per connection.

```json
// request (jean_mcp_stdio.rs:62)
{ "token": "...", "source": "<session-id|anon>", "depth": <u32>,
  "name": "<tool>", "arguments": { ... } }
// success (jean_mcp_core.rs:1424)
{ "jsonrpc": "2.0", "id": null, "result": { ... } }
// error (jean_mcp_core.rs:1428)  or bare {"error":"unauthorized"} for transport failures
{ "jsonrpc": "2.0", "id": null, "error": { "code": -32000, "message": "..." } }
```

Auth: bearer token generated by the parent, stored in `JeanMcpSocketHandle.token`, injected into the child's env. Mismatch → `{"error":"unauthorized"}`.

### 1e. Depth cap (the recursion brake)

```rust
// jean_mcp_core.rs:21
pub const JEAN_MCP_DEPTH_ENV: &str = "JEAN_MCP_DEPTH";
// jean_mcp_core.rs:58
pub fn current_depth() -> u32 {
    std::env::var(JEAN_MCP_DEPTH_ENV).ok().and_then(|v| v.parse().ok()).unwrap_or(0)
}
pub fn next_depth() -> u32 { current_depth().saturating_add(1) }
```

Flow:
1. The stdio proxy **reads** `JEAN_MCP_DEPTH` from its env and passes it verbatim in the socket request (`jean_mcp_stdio.rs:57`, `depth` field). It never increments.
2. The socket server reads `body.depth` back (`jean_mcp_socket.rs:266`) and passes it to `call_tool`.
3. Enforcement is **only for spawning tools** — `RATE_LIMITED_TOOLS` = `{cancel_session_run, create_session, send_chat_message, create_worktree}` (`jean_mcp_core.rs:24`). In `call_tool` (`:171`):
   ```rust
   if RATE_LIMITED_TOOLS.contains(&name) && depth > prefs.jean_mcp_max_depth {
       return Err(ToolError::internal(format!(
           "Jean MCP recursion depth {depth} exceeds limit {}", prefs.jean_mcp_max_depth)));
   }
   ```
   `jean_mcp_max_depth` is a user-configurable `AppPreferences` field. Read-only tools are exempt.
4. **Increment happens when a parent spawns a child.** When a jean session gets its `--mcp-config`, the injected env sets `JEAN_MCP_DEPTH = next_depth().to_string()` (current + 1) — `chat/jean_mcp.rs:32`. So depth 0 = user's top session, depth 1 = its sub-agent, etc. Persistent installs seed `"0"`.

Also a per-`source::tool` sliding-window rate limit (60 s, `prefs.jean_mcp_rate_limit_per_minute`), orthogonal to depth.

### 1f. How the spawned CLI gets the tools

Runtime injection (the recursion path) — `chat/jean_mcp.rs`:

```rust
// chat/jean_mcp.rs:19
fn build_jean_mcp_entry(app, session_id) -> Value   // one mcpServers entry
// chat/jean_mcp.rs:54
pub fn merge_into_mcp_config(app, session_id, existing: Option<String>) -> Option<String>
```

produces a `--mcp-config` JSON merged under `mcpServers`:

```json
{ "mcpServers": { "jean": {
    "type": "stdio",
    "command": "<stable launcher path>",
    "args": ["--jean-mcp-stdio"],
    "env": {
      "JEAN_MCP_SOCKET": "<socket path>",
      "JEAN_MCP_TOKEN":  "<auth token>",
      "JEAN_MCP_SESSION": "<real session id>",   // enables get_current_context
      "JEAN_MCP_DEPTH":  "<next_depth()>"        // <-- increment site
    } } } }
```

Persistent install (`jean_mcp_config.rs`) writes the same shape into the CLI's own config (Claude: `~/.claude.json` `mcpServers`), but with `JEAN_MCP_SESSION="manual-prod"` and `JEAN_MCP_DEPTH="0"`.

## 2. What the Burrow MCP server exposes

Same architecture — **reuse it wholesale**. New Rust modules mirroring jean:

| jean file | Burrow file | role |
|---|---|---|
| `jean_mcp_core.rs` | `src-tauri/src/burrow_mcp_core.rs` | registry + `call_tool` dispatch + depth const |
| `jean_mcp_stdio.rs` | `src-tauri/src/burrow_mcp_stdio.rs` | `--burrow-mcp-stdio` proxy |
| `jean_mcp_socket.rs` | `src-tauri/src/burrow_mcp_socket.rs` | in-process Unix-socket server |
| `chat/jean_mcp.rs` | inline in `lib.rs` (spawn path) | `--mcp-config` assembly |

The stdio proxy is launched via the **existing `burrow` binary** (it is already `include_str!`'d and written to `ensure_burrow_bin()`; add a `--burrow-mcp-stdio` flag that execs the Rust entrypoint — but note the CLI is a `sh` script, not the Rust exe). Simpler: the stdio proxy is the **Tauri app exe** itself (like jean), reached via `get_stable_launcher_command()`. See §3.

### 2a. Tool set → existing request-dir actions

Each MCP tool maps to a `SpawnRequest` kind already handled by `take_spawn_requests` (`lib.rs:1492`) or to a Rust-answered control command. The socket server's `call_tool` **writes the same request dir the CLI writes today**, then (for blocking tools) polls `<token>.done` — i.e. the MCP layer is a typed front-end over the identical file transport, so the frontend poll needs zero changes.

| MCP tool | args | maps to | today's CLI | answered |
|---|---|---|---|---|
| `spawn` | `{cmd, cwd?, token?, wait?}` | kind `spawn` → new tab | `burrow spawn` | frontend (new tab) |
| `create_worktree` | `{branch, base?, path?}` | kind `worktree` → `createWorktree` | `burrow worktree` | frontend |
| `list_workspaces` | `{}` | Rust DB query | `burrow list-workspaces` | Rust (`write_control_result`) |
| `list_tabs` | `{ws?}` | Rust DB query | `burrow list-tabs` | Rust |
| `send_to_tab` | `{tabid, text}` | **new** — write to a PTY | *(none today)* | Rust → `write_pty` |
| `focus_tab` | `{tabid}` | kind `focus-tab` | `burrow focus-tab` | frontend |
| `focus_workspace` | `{wsid}` | kind `focus-workspace` | `burrow focus-workspace` | frontend |
| `new_tab` | `{ws?, cmd?}` | kind `new-tab` | `burrow new-tab` | frontend |
| `collect_results` | `{tokens?}` | read `<token>.result`/`.done` | `burrow collect` | Rust (read + consume) |
| `wait_result` | `{token, timeout?}` | poll `<token>.done` | `burrow wait` | Rust (blocking) |
| `worktree_remove` | `{branch?, path?, force?}` | `remove_worktree_by` | `burrow worktree-remove` | Rust |
| `pr_create`/`pr_list`/`pr_view`/`pr_merge` | … | `gh_in` | `burrow pr-*` | Rust |

**Spawning tools** (subject to depth cap) = `{spawn, create_worktree, new_tab}`. Everything else is read/observe/route and exempt — same split as jean's `RATE_LIMITED_TOOLS`.

`send_to_tab` is genuinely new (no CLI equivalent): the socket server calls the existing `write_pty(tabid, text)` Tauri command directly. Lets a Manager agent drive an existing sub-agent tab, not just spawn fresh ones.

### 2b. Result collection — the real win

Today: agent runs `burrow spawn --token T … && burrow wait T`. With MCP: `spawn({wait:true})` blocks in the socket server on `<token>.done` and returns the captured result **as the tool result** — no second call. Or fire-and-forget `spawn({})` + later `collect_results({tokens:[...]})`. The `<token>.result`/`.done` capture mechanism (Stop-hook `burrow capture`, `bin/burrow:395-433`) is unchanged; MCP just reads those files in Rust instead of the agent shelling out.

### 2c. `call_tool` sketch (Burrow)

```rust
// burrow_mcp_core.rs
pub fn call_tool(app: &AppHandle, name: &str, args: Value, source: &str, depth: u32)
    -> Result<Value, String>
{
    const SPAWNING: &[&str] = &["spawn", "create_worktree", "new_tab"];
    let max = prefs(app).burrow_mcp_max_depth;           // default 3
    if SPAWNING.contains(&name) && depth > max {
        return Err(format!("Burrow MCP recursion depth {depth} exceeds limit {max}"));
    }
    match name {
        "spawn" => {
            let token = write_spawn_request_dir(app, &args, depth)?;  // same files bin/burrow writes
            if args.get("wait").and_then(Value::as_bool).unwrap_or(false) {
                block_on_done(app, &token, timeout)                   // read <token>.result
            } else { Ok(json!({ "token": token, "status": "spawned" })) }
        }
        "list_workspaces" => list_workspaces_rust(app),               // reuse lib.rs:1530 body
        "send_to_tab"     => { crate::write_pty(args.tabid, args.text)?; Ok(json!({"ok":true})) }
        // …
    }
}
```

`write_spawn_request_dir` is a Rust port of `bin/burrow`'s spawn arm (writes `cmd`/`token`/`cwd`/`ws`/`ready`) so the existing `Terminal.vue` poll claims it identically. The routing key `ws` = the source session's `BURROW_CWD` (carried in the socket request, like jean's `source`).

## 3. How a Burrow-spawned claude gets the tools + depth cap

When Burrow spawns a claude tab (the `spawn` handler above, or the button-launch path), inject `--mcp-config`:

```rust
// lib.rs, near the spawn/create_pty path
fn build_burrow_mcp_config(app: &AppHandle, ws_cwd: &str, depth: u32) -> String {
    serde_json::json!({ "mcpServers": { "burrow": {
        "type": "stdio",
        "command": get_stable_launcher_command(),   // app exe path, "burrow" fallback
        "args": ["--burrow-mcp-stdio"],
        "env": {
            "BURROW_MCP_SOCKET": socket_path(app),
            "BURROW_MCP_TOKEN":  socket_token(app),
            "BURROW_MCP_SESSION": ws_cwd,            // routing key = BURROW_CWD
            "BURROW_MCP_DEPTH":  (depth + 1).to_string()   // <-- increment
        } } } }).to_string()
}
```

- The **app exe** grows a `--burrow-mcp-stdio` branch in `main()` (before Tauri builder) that runs `burrow_mcp_stdio::run_stdio_server()` and exits — exactly jean's pattern. This is separate from the `sh` `burrow` CLI script; the stdio proxy is the compiled binary.
- Depth read from the spawning PTY's own `BURROW_MCP_DEPTH` env (0 if the top session was launched by a human). `next_depth()` = `current + 1` written into the child. A depth-`N` agent calling `spawn` when `N > burrow_mcp_max_depth` gets a tool error instead of a runaway fan-out.
- `burrow_mcp_max_depth` — new pref, default **3** (mirrors the existing soft `max_agents=3`), surfaced in Settings.
- Socket + token created once at Tauri `setup` (alongside `start_hook_server`), path `<BURROW_HOME_DIR>/burrow-mcp.sock`, token in `<BURROW_HOME_DIR>/burrow-mcp.token`. Reuse `BURROW_HOME_DIR` plumbing.

Persistent install (optional, later): a `~/.claude.json` `mcpServers.burrow` entry with `DEPTH="0"` so a hand-typed `claude` inside a Burrow PTY also gets the tools. Mirror `install_status_hooks` merge style (non-destructive, `.burrow-bak`). **Defer** unless wanted — the runtime `--mcp-config` covers button/agent spawns, which is the recursion case.

## 4. Migration path (keep file-based `burrow spawn` alive)

The MCP layer is **additive** — it writes the same request dirs and reads the same result files. Nothing about `take_spawn_requests` or `Terminal.vue`'s poll changes. So both transports coexist with zero frontend churn.

**Phase 0 — nothing removed.** Ship `burrow_mcp_{core,stdio,socket}.rs` + socket startup at `setup` + `--burrow-mcp-stdio` exe branch + `build_burrow_mcp_config`. Inject `--mcp-config` into **newly spawned** claude tabs only. The `burrow` sh CLI, the skill doc, `burrow wait/collect/spawn` all keep working untouched. Both paths hit `write_spawn_request_dir` semantics → `Terminal.vue` → same tabs.

**Phase 1 — prefer MCP in docs.** Update the global skill (`BURROW_SKILL_MD` in `lib.rs`) to teach the MCP tools first, with the CLI as the documented fallback. Agents naturally migrate; the depth cap starts protecting the common case.

**Phase 2 — depth cap on the CLI too (optional).** Have `bin/burrow`'s `spawn`/`worktree` arms read `BURROW_MCP_DEPTH` and refuse when over the limit, so the file path gains the same brake. Small `sh` guard, no Rust change.

**Phase 3 — deprecate (only if desired).** Once telemetry shows agents use MCP, mark the CLI spawn subcommands deprecated in the skill doc. Keep them — they're a no-tty-required fallback (agent subprocesses with no controlling tty can still shell out; MCP stdio needs the CLI to be an MCP client, which claude/codex are but ad-hoc scripts aren't). **Recommendation: never fully remove** — the file transport is the robust floor.

**Rollback:** drop the `--mcp-config` injection line. Everything reverts to file-only. No schema/DB migration involved.

## 5. Decisions (RESOLVED 2026-07-02)

1. **Stdio proxy binary → app exe.** Route the MCP proxy through the **compiled app exe** (`--burrow-mcp-stdio` branch in `main()`), NOT the `sh` script. The `sh burrow` CLI stays as the no-tty fallback. (Matches jean; no JSON-RPC in `sh`.)
2. **`send_to_tab` → any depth-0 session may write.** Not gated to Manager only. Same power a human at the keyboard has. The depth cap already brakes *spawning*, not writing.
3. **Depth default → 3.** Matches the existing soft `max_agents=3`. `burrow_mcp_max_depth` pref, surfaced in Settings.
4. **Windows → Unix socket only.** `#[cfg(windows)]` stub returns "unsupported". macOS-first (CLAUDE.md), YAGNI.
5. **Result capture parity → live-check before Phase 1, not a blocker for Phase 0.** MCP `spawn({wait})` relies on the existing Stop-hook `burrow capture` writing `<token>.result`; it should fire for MCP-spawned tabs (same tab, same `resultToken` sidecar). Verify live before flipping docs to prefer MCP.
